## Context

对 279 个术语名的实测（大小写归一词元、逐条与现有别名对账）：

- 131 个唯一词元，106 个出现 ≥2 次，25 个孤例
- 幂类型层 95 个术语 100% 规则化（`XType` = 基名+类型；`XTypeType` = 中间名+的类型）
- 实体层顺序拼接 71.7%，补「的类型」规则后 ≈86%
- **关联层顺序拼接仅 22.6%，加 `by`/`of` 语序规则后 34%** —— 瓶颈是句式，不是词表

因此本变更确立三层模型，并把「组合结果必须能复现现有别名」变成可执行的覆盖率门限。

## Goals / Non-Goals

**Goals**

- 131 个词元全部登记为数据元或限定词，**无未登记词元**（构建期强制）
- 组合器能从词表 + 模板确定性地生成规范中文名，实体与关联的精确复现率均 **≥ 90%**
- 组合结果与现有别名层的差异**逐条可见**（不是静默取近似）
- 新术语若由既有词元组成 → 自动获得规范名；否则构建失败并要求登记新词元

**Non-Goals**

- P1 不改运行时检索（`terms.json` 字段、CLI 输出、`zh_aliases` 检索路径全部不动）
- 不引入分词库/NLP：词元分解只用 CamelCase 规则与词表
- 不删除现有 279 条别名（降级为显示/同义词层）
- 不做中英双向翻译生成（中文名是策展 + 组合，不是机器翻译）

## Decisions

### Decision 1: 三层模型，而不是「数据元 + 限定词」两层

**选择**：`elements`（对象类）+ `qualifiers`（结构词与关系谓词）+ `templates`（关系模板表）。

**理由**：实测关联层两层模型只能到 34%，失败样例全是语序问题（`activityPartOfCapability` 拼成「能力的活动属于」）。中文关系式有独立句式（`X属于Y`、`X由Y执行`、`X由Y实现`、`X在Y下可执行`），必须由模板承载，词表无法表达。

**Alternatives**：A. 只做两层（拒绝：关联 34%，不达标）；B. 逐条写模板而不用词表（退化成手写别名，失去组合与归一价值）。

### Decision 2: 词表是权威源，构建期强校验

**选择**：`dm2-reference/dm2-element-vocabulary.yaml` 为唯一来源；`build_knowledge_indexes.py` 校验 `terms.json` 中每个词元都已登记，模板必须良构（槽位、连接词、中文模板齐备），违规即构建失败。

**理由**：与 `dm2-term-zh-aliases.yaml` 同构——「缺一条就静默降级」的失败模式必须变成显式失败。同时保证新增术语不能悄悄绕过模型。

### Decision 3: 组合算法 = 最长连接词优先 + 对象类拼接 + 结构规则

**选择**：

1. 词元分解（CamelCase 规则，casefold 归一）；
2. 在词元序列中查找**连续连接词**（`connectors`），取**最长匹配**的模板；槽位 A/B 吸收连接词前后的词元串，递归组合；
3. 无模板命中时走对象类拼接：逐词元取中文直接相连；
4. 结构规则：结尾 `type type` → `{前缀}的类型`；结尾单个 `type` → `{前缀}类型`。

**理由**：模板用「连接词 + 槽位」而非定长模式，才能吸收任意长度的主语/宾语（`activityPartOfProjectType` 的宾语是 `project type` 两个词元）。最长匹配保证 `is realized by` 不会被 `by` 抢先。

### Decision 4: 对账门限写进测试，差异必须可见

**选择**：`test/test_element_vocabulary.py` 断言实体 ≥90%、关联 ≥90% 的**精确复现**（组合名等于别名层首选名，或等于其任一别名）；失败时打印全部差异（术语、组合名、别名层现值）。

**理由**：把「模型是否自洽」变成可执行断言，同时保留人工复核入口——差异清单就是待办的词元/模板修订清单。

### Decision 5: 别名层保留，角色降级

**选择**：现有 `zh_aliases` 继续用于检索与显示；组合层产出**规范名**（P2 起作为检索归一的锚点与 `--explain` 的解释依据）。

**理由**：组合覆盖率先到 90%，直接替换检索会引入回归；两层并存还能持续对账（别名层是组合层的回归测试基准）。

## Risks / Trade-offs

- **[风险] 25 个孤例词元无法组合**（如 `GeoPoliticalExtent` 的 `geo`+`political` 选词争议）→ 孤例单独登记为数据元，组合规则不强行套用；差异清单暴露它们。
- **[风险] 模板表膨胀成新的手写层** → 模板以「连接词序列」为单位（46 个关系词元 → 约 25–35 个模板），远小于 106 条关联；门限测试防止它悄悄变成逐条映射。
- **[取舍] 组合名与人工别名风格可能不一致**（如 `GeoPoliticalExtent` 应为「地缘政治范围」而非「地理政治范围」）→ 通过词元译名修订吸收，而不是加特例模板。

## Migration Plan

- **P1（本变更）**：词表 + 组合器 + 构建校验 + 对账门限。运行时零改动。
- **P2**：`terms.json` 增加 `canonical_zh`；检索侧接入词元归一与组合式扩展召回（修改 `dm2-metamodel-knowledge`）。
- **P3**：反向分解（中文查询 → 数据元 + 限定词）+ `--explain` 命中理由。
- **P4**：新术语自动生成规范名；未覆盖即构建失败（替代「必须手写别名」）。

## Open Questions

- 组合名与别名层首选名冲突时，谁进 `canonical_zh`？**当前默认**：组合名进规范层，别名层保留全部人工写法；冲突记入对账报告。
- 是否需要为 25 个孤例词元建立「不可组合」白名单并在报告中单独统计？**当前默认**：登记为数据元即可，不额外分类。
