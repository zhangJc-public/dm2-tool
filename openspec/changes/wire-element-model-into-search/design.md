## Context

P1 建立了数据元/限定词模型（131 词元 + 39 模板）与组合器，对账结果实体 100%、关联 96.2%。但检索路径没有用它：实测 `能力 活动` 的首条是 `Activity`（靠数据组别名命中），真正的关系术语排在后面；规范名也不在检索面内。

## Goals / Non-Goals

**Goals**

- 查询片段能归一为数据元/限定词，从而中英双向、同义写法都能召回同一概念
- 「活动 + 能力」这类**结构化**查询把关系术语排到纯子串命中之前
- 组合出的规范名（`canonical_zh`）可检索
- 子串召回**不回退**：兜底层保留，仅排序变化

**Non-Goals**

- 不做查询分解的**解释输出**（`--explain`）——留给 P3
- 不做拼音/错别字/同义词自动扩展（词表之外不猜）
- 不改 `knowledge term/taxonomy/...` 的输出形状
- 不做视图名/数据组名的中文检索（仍待另开变更）

## Decisions

### Decision 1: `canonical_zh` 进派生索引，不进运行时计算

**选择**：构建期用组合器算出 `canonical_zh` 写入 `terms.json`；运行时只读。

**理由**：符合「运行时只加载紧凑 JSON、不解析权威源」的既有规则；组合是纯函数，构建期算一次即可，且能被快照测试守护（词表改了没重跑构建 → 测试失败）。

### Decision 2: 反查表放在 `ElementVocabulary`，一对多

**选择**：`load()` 时构建 `reverse: {中文词条: [词元, ...]}`（含复合数据元的中文）。查询片段命中反查表即得到**候选词元集合**。

**理由**：中文词条天然一对多（`区域` 同时对应 `area`/`region`，`活动` 同时对应 `activity`/`action`），一对多必须表达为「段内 OR」，否则会把正确术语排除。

### Decision 3: 结构化匹配 = 段内 OR、跨段 AND，作为独立层级

**选择**：查询按既有规则分词后逐段处理——能归一为候选词元的段用「术语词元集合与之相交」判定，不能归一的段回退子串；所有段都要满足（AND）。命中层级：

| 层 | 判定 |
|---|---|
| 0 | 术语名或**完整别名**精确相等 |
| 1 | 术语名/别名内子串 |
| 2 | **结构化匹配**（查询片段归一为词元） |
| 3 | 仅定义/数据组/规范名子串 |

**理由**：`能力 活动` 在层 2 命中 `activityPartOfCapability`、`activityMapsToCapabilityType`（词元同时含 capability 与 activity），而 `Activity` 只含 activity 词元 → 落到层 3，排序自然靠后。既提高精度，又不丢召回。

### Decision 4: 兜底层必须保留

**选择**：任何一段无法归一（例如 `主体` 不在词表中文里）时，该段仍走子串匹配。

**理由**：词表是策展的、不完整；归一失败不能变成召回失败。既有测试（`资源流`、`Actor`、`01-performer`）全部依赖子串路径，保留即零回归。

## Risks / Trade-offs

- **[风险] 限定词归一放大召回**（`类型` → `type` 词元 → 157 个术语）→ 结构化层排在名称/别名层之后，且这是**正确**的结构召回（真的含 `type` 词元）；不额外做抑制。
- **[风险] 排序变化破坏既有断言** → 既有测试断言的是「命中集合包含」与「首条为某术语」，实施后必须全绿；若某条依赖旧排序，评估后按语义修正并说明。
- **[取舍] 构建脚本要 import `dm2`** → 用 `sys.path.insert(0, ROOT/"src")` 保证未安装也能跑，仍保持「脚本可独立执行」。

## Migration Plan

- P2 只改检索与派生索引；`dm2 init` 的新项目直接拿到带 `canonical_zh` 的 `terms.json`，旧项目重跑 `dm2 init` 或复制索引即可。
- P3（查询分解与 `--explain`）、P4（新术语自动命名）随后。
